# Пользовательские сценарии

Все сценарии описаны по фактическим маршрутам (`portal/routers/*.py`) и
шаблонам. Портал многопользовательский (два обычных пользователя и один
админ, в коде — под реальными именами владельца портала), но без общего
проекта/команды — каждая тренировка/протокол принадлежит
конкретному «предметному» пользователю (см.
[«Видимость данных»](./architecture.md#видимость-данных-multi-user-на-одной-базе)).

## 1. Вход

`GET /login` показывает список всех пользователей (`list_all_users`) —
выбор без пароля. `POST /login` со скрытым `user_id` ставит cookie
`portal_user_id` (год жизни, `httponly`, `samesite=lax`) и редиректит на
`/`. Если задан `ORIENTEERING_PORTAL_AUTO_LOGIN`, экран логина можно вообще
не увидеть — вход произойдёт автоматически по имени пользователя из env.

## 2. Создание тренировки: пошаговый мастер

Мастер строится вокруг черновика `training_import_drafts`; шаг не
сохраняется в `trainings`, пока пользователь не дойдёт до финализации.

1. **`GET /trainings/new` → `POST /trainings/imports`** (шаблон
   `training_import_details.html`): название, дата, `training_type`
   (свободный текст, `rogaine` — специальный случай для разметки КП),
   `discipline` (`run`/`bike`/`ski`), место, заметки, и — только у
   админа — выбор, **для кого** создаётся тренировка
   (`subject_user_id`, кому будет видна запись). Создаёт черновик
   (`create_import_draft`) и редиректит на шаг карты.
2. **`GET /trainings/imports/{draft_id}/map`** (`training_import_map.html`):
   - `POST /api/imports/{draft_id}/map-image` — загрузка скана карты
     (допустимые расширения: `.jpg`/`.jpeg`/`.png`/`.webp`,
     `ALLOWED_MAP_SUFFIXES`), сохраняется в `UPLOAD_DIR`.
   - **Геопривязка** (`static/georef.js` + `POST /api/imports/{draft_id}/georef`
     и сервис `services/georef.py`): пользователь ставит ≥3 пары точек
     «пиксель картинки ↔ гео-координата» на двух областях экрана (скан
     слева, базовая карта справа); `fit_affine_transform` считает
     аффинное преобразование методом наименьших квадратов, `residuals_meters`
     возвращает ошибку в метрах по каждой точке для проверки качества.
   - **Контрольные точки дистанции** (`POST .../course-controls`):
     расставляются на карте кликами; автоматически получают метки
     С/К/Ф/номер и тип по позиции в списке (`course_control_label`/`kind`
     — правила для обычной дистанции и для рогейна разные, см.
     [`data-model.md`](./data-model.md)).
   - **Несколько слоёв карты**: `POST /api/imports/{draft_id}/map-layers`
     добавляет ещё один слой (например, если дистанция сфотографирована
     по частям) — у каждого слоя свои картинка, геопривязка и свои КП.
3. **`GET /trainings/imports/{draft_id}/track`** (`training_import_track.html`,
   `static/track.js`): `POST /api/imports/{draft_id}/track-gpx` — загрузка
   GPX-файла (`ALLOWED_TRACK_SUFFIXES = {".gpx"}`), разбирается
   `parse_gpx_track_points` в список точек `{lat, lon, ele, time}`.
   Можно поправить/сохранить точки (`POST .../track-points`) или удалить
   трек и начать заново (`POST /trainings/imports/{draft_id}/track/delete`).
4. **`POST /trainings/imports/{draft_id}/finish`** → `finalize_import_draft`:
   создаёт (или обновляет, если это правка/`edit_training_id`) запись в
   `trainings`, зеркалит первый полный слой карты в legacy-таблицы
   `maps`/`map_georeferences`, проставляет видимость
   (`_seed_training_visibility`) — и редиректит на плеер тренировки.

**Редактирование** существующей тренировки (`GET /trainings/{id}/edit`) и
**клонирование** (`GET /trainings/{id}/clone`, например чтобы быстро
завести похожую тренировку с той же картой) переиспользуют тот же мастер —
создаётся новый черновик, предзаполненный данными исходной тренировки
(`create_edit_import_draft` / `create_clone_import_draft`), и открывается
сразу на шаге деталей.

## 3. Плеер тренировки (`GET /trainings/{id}/play`)

`templates/training_player.html` + `static/player.js`. Показывает карту
(слой(и) с геопривязкой) с наложенным треком и дистанцией. Возможности,
подтверждённые в JS/шаблоне и `ВОЗМОЖНОСТИ_ПОРТАЛА.md`:
воспроизведение прохождения с изменяемой скоростью, перемотка ползунком,
отображение текущего темпа по ходу движения, обрезка начала/конца трека с
возможностью отмены и сохранением через `POST /api/trainings/{id}/track-points`
(`update_training_track_points`). Если к тренировке уже привязан протокол
(`get_latest_race_result_for_training`), плеер также получает разрывы по
сплитам относительно лидера (`_race_result_split_gaps`) для наглядности.

## 4. Импорт протокола соревнования

Два входа: самостоятельно (`/race-results/import`) или из карточки
тренировки (`/trainings/{id}/race-result/import`, тогда дата подставляется
из тренировки и протокол сразу привязывается к `training_id`).

1. **Ссылка на протокол** (`POST .../import/preview`, форма — URL и,
   опционально, дата старта) → `_load_protocol()` скачивает и парсит
   протокол (см. [`integrations.md`](./integrations.md) про форматы и
   Orgeo/sportident.online). При ошибке (неподдерживаемый URL, сеть,
   формат) — та же страница с текстом ошибки, `400`.
2. **Превью** (`race_result_preview.html`): показываются найденные группы
   протокола; пользователь выбирает свою группу и свою строку
   (`self_row_index`) — то есть портал не знает заранее, кто из
   участников «свой», это ручной выбор при каждом импорте.
3. **`POST .../import/save`** (`_race_result_import_save`): сохраняет
   выбранную группу целиком в `race_results` (`save_race_result`),
   автоматически определяет видимость по совпадению имени участника с
   пользователями портала (`_seed_race_result_visibility`), редиректит на
   страницу протокола.
4. Альтернативно — **прикрепить уже сохранённый протокол** к тренировке
   без повторного импорта: `POST /trainings/{id}/race-result/attach` с
   `race_result_id` из списка «доступных для прикрепления»
   (`_list_attachable_results` — сохранённые протоколы этого же
   пользователя без тренировки или ранее привязанные к этой же).

### Обратный поиск: «граббер» (`/race-results/grabber`)

Вместо готовой ссылки — ввод ФИО спортсмена; портал сам обходит календарь
и (опционально) до 3 последних лет архива `o-site.spb.ru`, находит все
сплит-страницы, где встречается это имя, и выводит список с прямой
ссылкой на предзаполненное превью импорта (`/race-results/import/open`).
Уже импортированные старты в списке результатов помечаются отдельно
(`_annotate_grabber_matches`). Подробности алгоритма —
[`integrations.md`](./integrations.md#поиск-стартов-участника-граббер-race_grabberpy).

## 5. Просмотр протокола и сравнение участников (`GET /race-results/{id}`)

`templates/race_result.html` (521 строка) — самая насыщенная страница:

- Полная таблица сплитов **всех участников группы**, не только «своих»
  (для `kind="course"` — по фиксированным этапам, включая эстафетные
  `lap`-варианты; для `kind="score"` — по взятым КП рогейна).
- Сравнение со сплитами лидера (виртуальный «идеальный» участник,
  `_virtual_leader_participant`) — отставание на каждом этапе,
  цветовая маркировка хороших/средних/проблемных сплитов
  (`_classify_gap_indexes` / `_classify_score_gap_indexes`).
- Суммарный проигрыш по проблемным сплитам (`_self_problem_total_gap` /
  `_score_self_problem_total_gap`).
- Диаграмма распределения темпа (`pace_distribution_dialog.js`,
  `_pace_distribution_view`) и диаграмма «достижимости» результата
  (`race_reachability_dialog.js`, `_reachability_chart_view`) — обе на
  Chart.js.
- Переход в плеер связанной тренировки одним кликом, если трек уже
  загружен.

## 6. Разбор проблемного сплита с AI-тренером

Точка входа — карточка «Сплиты на анализ» на дашборде (`/`, `/problem-splits`)
или таблица сплитов на странице протокола. Открывается модальное окно
`split-analysis-modal` (`static/split_analysis_dialog.js`, 1671 строка):

1. Показывается участок карты с треком по этому сплиту, направлением
   (стрелкой) и контрольными точками; можно переключить ориентацию карты
   по направлению движения (`#split-orient-toggle`), нарисовать свой
   вариант пути (`#split-draw-toggle`) для сравнения по длине, посмотреть
   график темпа по сплиту, экспортировать анимацию сплита как видео
   (`MediaRecorder`, если браузер поддерживает).
2. **Опрос причины ошибки**: выпадающий список причин из `error_reasons`
   (загружается через `/api/error-reasons`) плюс произвольный текст;
   сохраняется через `PUT /api/split-error-review` с debounce — без
   отдельной кнопки «сохранить». Уже сохранённый разбор подгружается через
   `POST /api/split-error-review/get` при открытии диалога.
3. **Диалог с AI-тренером**: кнопка «Начать диалог» → свободные вопросы →
   `POST /api/split-analysis/chat` (снимок карты + параметры сплита +
   история + вопрос). Подробности — [`ai-coach.md`](./ai-coach.md).

Реализует идею «Опросник по проблемным сплитам» из `docs/ideas.md` (пункт
2) — на момент написания этого документа она уже реализована, а не просто
задумана.

## 7. Дашборд, аналитика по причинам и позициям (`GET /`)

Три виджета, собираемые в `portal/main.py` из всех видимых пользователю
результатов (`list_dashboard_race_results`):

- **Сплиты на анализ** — топ проблемных сплитов по величине отставания
  от лидера среди тренировок с полной картой+треком+КП, ещё не разобранных
  через опросник (`_dashboard_training_ready`, `_build_problem_splits`).
  Отдельная страница `/problem-splits` показывает их все без лимита.
  Уже разобранные (с сохранённой причиной) переезжают на `/reviewed-splits`
  (с фильтром по причине через query-параметры `reason_id`/`custom_reason`).
- **Причины ошибок** — частота причин из сохранённых обзоров, тренд по
  датам стартов, автотекст-инсайт про самую частую причину
  (растёт/снижается) — `_build_error_reason_stats`.
- **Позиции в протоколах** — место (или расчётное место для эстафетных
  курсов по фактическому времени) относительно числа участников по датам
  стартов, лучшее и последнее место — `_build_race_position_stats`.

## 8. Администрирование (только `is_admin`, `/settings/*`)

- `/settings/users` — список пользователей, создание, редактирование
  (кроме самого админа), удаление.
- `/settings/error-reasons` — список причин ошибок сплитов, добавление,
  переименование, включение/выключение (`is_active`) без физического
  удаления.

## Что не реализовано (в сравнении с `docs/ideas.md`)

Из бэклога идей владельца на момент написания этого документа явно
**не найдено** в коде:

- Идея 3 (план тренировок на основе статистики причин ошибок) — дашборд
  считает статистику причин, но рекомендаций/плана тренировок на её основе
  портал не формирует.
- Идея 4 (виртуальные «идеальное 2/3 место» в проблемной таблице) — есть
  только один виртуальный лидер (`_virtual_leader_participant`).
- Идея 6 (геопривязка карты напрямую к треку, без спутниковой подложки) —
  геопривязка всегда идёт через пары «пиксель ↔ гео-координата» на базовой
  карте (`services/georef.py`); привязки «по КП на треке» не найдено.

Идея 1 (автоматическая таблица сплитов на экране трека) и идея 5
(рисование альтернативного варианта пути в разборе сплита) — судя по коду
(`track_split_markers.js`, `split_analysis_dialog.js` с `drawMode`/
`altRoutePoints`), реализованы, хотя бы частично.
